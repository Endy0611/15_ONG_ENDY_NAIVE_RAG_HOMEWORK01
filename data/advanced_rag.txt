Advanced RAG Techniques Beyond the Naive Pipeline

A naive RAG pipeline embeds the question once, searches the vector store once, and hands the top-k chunks straight to the language model. This works as a baseline, but it has known weaknesses, and several advanced techniques exist specifically to address them.

Re-ranking adds a second pass after the initial retrieval step. Instead of trusting the raw similarity scores from the vector search, a separate re-ranking model looks at the question and each retrieved chunk together and scores how relevant that chunk really is. This catches cases where a chunk is close in embedding space but not actually useful for answering the question, and it lets the system keep only the truly best chunks before generation.

Query rewriting changes the question before it is even embedded and searched. A user's original question might be short, ambiguous, or phrased very differently from how the documents describe the same topic. A query rewriting step, often another call to a language model, can expand the question, break it into sub-questions, or rephrase it to better match the vocabulary used in the documents, which tends to improve what the retriever finds.

Hybrid search combines the semantic vector search used in naive RAG with traditional keyword-based search. Vector search is good at matching meaning even when the wording is different, but it can sometimes miss an exact term, like a product code or an acronym, that a keyword search would catch immediately. Running both searches and merging the results tends to be more robust than relying on either one alone.

Multi-hop retrieval is useful when a single question actually requires information from more than one part of the documents, or even from more than one document, to answer fully. Instead of a single retrieve-then-generate pass, the system retrieves an initial set of chunks, uses them to figure out what additional information is still needed, and performs one or more follow-up retrievals before generating the final answer.

Each of these techniques adds complexity and usually extra latency, since they involve additional model calls or search passes. They are typically introduced only after a naive RAG baseline has been built and its specific weaknesses, like poor retrieval precision or missed multi-part answers, have actually been observed.
