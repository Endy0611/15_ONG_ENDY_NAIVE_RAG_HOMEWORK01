Vector Databases and Embeddings for RAG

An embedding is a list of numbers that represents the meaning of a piece of text. Two chunks of text that mean similar things end up with embedding vectors that are close together in that numeric space, even if they use completely different words. This is what makes semantic search possible: instead of matching exact keywords, a RAG system can find chunks that are conceptually related to a question.

Embedding models are usually small, fast neural networks trained specifically to produce these vectors. In a local RAG setup, an embedding model can be run entirely on your own machine using a tool like Ollama, which removes the need to send your documents to an external API. The same embedding model must be used to embed both the document chunks during ingestion and the user's question during retrieval, otherwise the vectors will not be comparable.

A vector database is a specialized storage system built to hold large numbers of these vectors and search through them efficiently. Instead of scanning every vector one by one, a vector database uses indexing structures that let it quickly find the vectors most similar to a given query vector, usually measured with cosine similarity or Euclidean distance. Popular local options include ChromaDB, Qdrant, and Pgvector, each with different trade-offs around setup complexity, persistence, and scale.

When a chunk is stored in a vector database, it is usually saved along with metadata: the source filename, its position in the original document, and sometimes a timestamp. This metadata is what lets a RAG system tell the user which document an answer came from, and it is also useful for filtering results, for example limiting a search to only one category of document.

Choosing a good chunk size matters here too. Chunks that are too large dilute the embedding with unrelated information, making retrieval less precise. Chunks that are too small lose surrounding context, making the retrieved text hard for the language model to use on its own. A common starting point is a few hundred characters or tokens per chunk, with a small overlap between consecutive chunks so information near a chunk boundary is not lost.
